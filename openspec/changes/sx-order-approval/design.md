# Order Approval Capability Design

## User interface

No screen records were extracted for this capability; its user interface is unspecified. The order approval capability operates on behalf of the admin system and the POS system through XML message-based APIs.

## Overview

The order approval capability provides workflow-based order processing with automatic approval for small orders and manual approval capability for larger orders. It sits between order intake (from the Java Pet Store) and order fulfillment (supplier orders and customer notifications), implementing the business rules that determine whether an order should proceed immediately or await administrator decision.

## Architecture

### Message-driven design

The order approval workflow is implemented using three message-driven beans (MDBs) coordinated by JMS queues:

1. **PurchaseOrderMDB** — Entry point. Receives purchase orders from the Java Pet Store via `PurchaseOrderQueue`, parses XML, creates the PurchaseOrder EJB, and initializes workflow in PENDING status. Applies auto-approval thresholds (locale-based) and routes qualifying orders immediately to OrderApprovalQueue.

2. **OrderApprovalMDB** — Core approval engine. Processes approval batches from `OrderApprovalQueue`, validates that orders are in PENDING status, updates workflow status, and generates downstream messages for supplier orders and customer notifications.

3. **Transition delegates** (OrderApprovalTD, etc.) — Coordinate routing of outcomes to supplier queue and mail queue based on approval decision.

### Data model

**PurchaseOrder** — Entity bean containing order metadata (OrderId, UserId, OrderDate, TotalPrice, Locale) and relationships to ContactInfo and LineItem collections. Created during order intake.

**OrderApproval** — XML document model (not an entity) representing a batch of order approval/denial decisions. Contains ChangedOrder entries, each with OrderId and OrderStatus.

**ChangedOrder** — Lightweight value object representing a single order's approval decision (OrderId + OrderStatus).

**ProcessManager** — Workflow state machine. Maintains order status across the fulfillment lifecycle (PENDING → APPROVED/DENIED → SHIPPED_PART/COMPLETED).

### Workflow states

| State        | Meaning                           | Entry                                               | Exit                                          |
| ------------ | --------------------------------- | --------------------------------------------------- | --------------------------------------------- |
| PENDING      | Order received, awaiting approval | PurchaseOrderMDB.createManager()                    | OrderApprovalMDB.updateStatus()               |
| APPROVED     | Order approved (manual or auto)   | OrderApprovalMDB.updateStatus() (status = APPROVED) | InvoiceMDB.updateStatus() (first invoice)     |
| DENIED       | Order rejected by administrator   | OrderApprovalMDB.updateStatus() (status = DENIED)   | Terminal                                      |
| SHIPPED_PART | Order partially fulfilled         | InvoiceMDB.updateStatus() (incomplete shipment)     | InvoiceMDB.updateStatus() (all items shipped) |
| COMPLETED    | Order fully fulfilled             | InvoiceMDB.updateStatus() (all items shipped)       | Terminal                                      |

### Auto-approval thresholds

Small orders automatically proceed without administrator review:

- **US locale** — Orders with total price < 500 USD
- **Japan locale** — Orders with total price < 50000 (JPY assumed)

Orders meeting these thresholds trigger an immediate OrderApproval message with status APPROVED. Orders exceeding the thresholds remain PENDING for manual review.

### Reprocessing guard

OrderApprovalMDB implements a guard: it checks each order's current status before processing. Orders not in PENDING status are skipped. This prevents duplicate processing if approval messages are retried or replayed.

## Interfaces

### PurchaseOrderMDB input

**JMS Queue:** `PurchaseOrderQueue`  
**Message type:** TextMessage containing XML  
**XML format:** PurchaseOrder DTD (defined in xmldocuments component)

The PurchaseOrder XML includes OrderId, UserId, EmailId, OrderDate, Locale, TotalPrice, ContactInfo, and LineItem collection.

### OrderApprovalQueue (PurchaseOrderMDB → OrderApprovalMDB)

**Message type:** TextMessage containing OrderApproval XML  
**XML format:** OrderApproval DTD

Contains one or more Order entries with OrderId and OrderStatus. Generated by:

1. PurchaseOrderMDB for auto-approved orders
2. ApplRequestProcessor for admin-initiated approvals/denials (via AsyncSender)

### Admin approval interface (ApplRequestProcessor)

**Request format:** XML with request type and parameters  
**GETORDERS request:**

```xml
<Request>
  <Type>GETORDERS</Type>
  <Status>PENDING</Status>
</Request>
```

**UPDATESTATUS request:**

```xml
<Request>
  <Type>UPDATESTATUS</Type>
  <Order>
    <OrderId>ORD-001</OrderId>
    <OrderStatus>APPROVED</OrderStatus>
  </Order>
  <Order>
    <OrderId>ORD-002</OrderId>
    <OrderStatus>DENIED</OrderStatus>
  </Order>
</Request>
```

**Response format:** XML with order list or success/error status.

### Supplier integration output (OrderApprovalTD)

**JMS Queue:** `SupplierPurchaseOrderQueue`  
**Message type:** TextMessage containing TPA Supplier Order XML

For each approved order, a supplier PO is generated containing:

- Order ID, date
- Complete shipping address (given name, family name, street, city, state, country, zip, email, phone)
- All line items (category ID, product ID, item ID, line number, quantity, unit price)

### Customer notification output (OrderApprovalTD)

**JMS Queue:** `MailOrderApprovalQueue`  
**Message type:** TextMessage containing OrderApproval batch

Sends approval/denial decisions for both APPROVED and DENIED orders to mail system for customer notifications.

## Locale-aware processing

The system respects the purchase order's Locale attribute to apply locale-specific thresholds. Locale is captured during order creation and used by PurchaseOrderMDB to determine auto-approval eligibility. No currency conversion is performed; thresholds are assumed to be in the local currency of the locale.

## Transaction semantics

All message processing occurs within `Required` transaction scope (container-managed transactions). Each MDB.onMessage() call is a single atomic transaction:

- XML parsing and validation
- EJB creation/lookup
- Workflow state updates
- Message routing to downstream queues

Failures roll back the entire transaction, and the input message is retried by the container.

## Error handling

- **XML validation failure** — XMLDocumentException is thrown and caught by MDB, causing message retry
- **EJB lookup failure** — ServiceLocator exception is caught and message is retried
- **Database constraint violation** — Transactional rollback and retry (e.g., duplicate order ID)

Non-recoverable errors (e.g., malformed XML with no valid parse path) are logged and the message is typically moved to a dead-letter queue by the container.

## Design decisions

1. **Message-driven architecture** — JMS provides loose coupling between order intake, approval, fulfillment, and notification. Auto-approval can complete synchronously or asynchronously depending on thresholds.

2. **Status guard in OrderApprovalMDB** — The guard preventing reprocessing of non-PENDING orders is a defensive mechanism against message replay or duplicate delivery. It is simpler and safer than modifying the approval message format or introducing idempotency tokens.

3. **Auto-approval thresholds are hardcoded** — The thresholds (500 USD, 50000 JPY) are bare literals with no configuration source. This is a known limitation inherited from the legacy implementation and should be addressed in a future enhancement to support configurable thresholds.

4. **OrderApproval as XML document model** — Rather than defining an entity bean for approval decisions, OrderApproval is a lightweight XML document wrapper. This allows approval batches to be handled transactionally without requiring persistence, reducing complexity.

5. **Supplier PO generation during approval processing** — Supplier orders are generated synchronously within the approval message processing transaction. This ensures supplier orders are created exactly once for each approved order and eliminates the need for a separate fulfillment trigger.

6. **Transition delegates route outcomes** — OrderApprovalTD decouples the approval message processing (OrderApprovalMDB) from downstream routing (supplier queue, mail queue). This allows multiple transition paths without polluting the MDB with routing logic.
